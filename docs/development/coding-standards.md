# 通用编码规范与设计准则

## 架构与领域优先

在进入编码前，必须明确业务目标、领域边界、模块职责、依赖方向、数据流转、事务边界、故障表现与可验证工件。设计应面向长期可维护性，实现则保持克制，单一用例直接实现，延迟抽象至第二个真实用例出现。

---

## Ponytail 开发阶梯 (高效极简原则)

实现功能时，严格遵循以下递进顺序：
1. Python / TypeScript 语言特性与官方标准库；
2. 操作系统与平台原生机制；
3. 已有第三方依赖的原生 API 与内建能力；
4. 仅在真实领域边界处编写轻量适配器；
5. 只有在第二个明确用例验证后才引入新的抽象层。

严禁自行重复封装 pgvector、pg_search、FastAPI、Pydantic、SQLAlchemy、RabbitMQ、LangGraph、TanStack 或 S3 的已有内建能力。

---

## 删除优于兼容

内部代码重构时，直接删除过时路径，严禁保留废弃 shim、临时兼容包装或长期双写。对外稳定契约（`/api/*`）的变更按协议版本迁移流程执行。

---

## 命名与模块划分

- 命名必须反映领域语义：函数与方法使用动词，类与数据结构使用名词。
- 杜绝使用模糊名称（如 `data`、`info`、`manager`、`helper`、`utils`）。
- 模块应高内聚、单一职责，暴露精简稳定的公开接口，隐藏内部实现细节。

---

## 可观测性与日志

- 采用携带请求 ID、任务 ID、文档 ID 等上下文的结构化日志。
- **严禁泄露敏感信息**：密钥、密码凭据、签名 URL 或文档敏感全文绝对禁止打入日志。
- 所有外部依赖调用失败均应记录调用状态、延迟耗时、错误分类与重试决策。

---

## 质量验证准则

- 功能开发与重构期间依靠静态分析、严格类型检查、配置验证、schema 状态校验与逻辑测试快速验证，避免未自洽代码流入环境。
- 功能研发闭环后，必须通过真实容器环境的端到端验收测试验证（容器路径 + 就绪探针 + 真实问答），在系统中排查修复底层问题，严禁使用虚假 Mock 掩盖异常。
