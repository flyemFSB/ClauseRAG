## Defects the acceptance found, and what was done

The suite was run repeatedly *because each run exposed something*; every failure below was diagnosed
from the run's own logs before the next run, and the last two runs (8 and 9) were green.

1. **Harness: `-Full` was forwarded to every probe.** Run 2 failed at the first probe with
   "a parameter cannot be found that matches parameter name 'Full'": only `parsing`, `chunking` and
   `indexing` declare the switch. Fixed by giving the probe table a `Full` capability and forwarding
   the switch only to those three.
2. **Product (introduced in Phase 6 of this refactor, found by run 3): a public composition function
   changed shape without its inline callers.** Three probes write their own `redispatch.py` helper
   and still called `open_job_queue(settings)` after the tracing client became a parameter. Fixed by
   updating those three helpers.
3. **Harness (pre-existing, red in the pre-refactor baseline): the queue probe.** It compared the
   caller's topology against a hard-coded 5 containers (the topology has 8 services since the
   observability stack arrived) and asserted drained queues without waiting for the delivery that the
   previous step's lane had just appended. Fixed by comparing the running service *set* captured at
   the probe's start with the set at its end, and by draining through the probe's own
   `Wait-ForQueuesDrained` before the assertion.
4. **Harness: the graph probe read LightRAG's asynchronous state once.** Run 4 failed with "the graph
   processed 1 of 2 documents". Research (`docs/research/official-docs-lightrag.md` §40 and the
   installed 1.x source): `ainsert` enqueues and then calls
   `apipeline_process_enqueue_documents`, which **refuses the slot when another run already holds
   `busy` and returns early** — so "the build was accepted" is not "the documents were processed",
   and the build cannot promise the latter. Fixed in the probe with a bounded (90 s) poll of
   `lightrag_doc_status`; the assertion itself is unchanged.
5. **Product (introduced in Phase 6 of this refactor, found by run 5): Taskiq could not resolve the
   injected class's type hints.** The worker wrote
   `RuntimeWarning: Cannot resolve type hints for a class DocumentIngestion` to stderr, which the
   queue probe asserts against. Cause: `taskiq_dependencies` resolves the dependency's hints at run
   time, and `UUID`/`GraphBuildOutcome` were imported under `TYPE_CHECKING` only. Fixed by importing
   them at run time and disabling the typing-only rules for that module, with the reason written where
   it is needed (the same treatment `agent_runtime/state.py` already documents for LangGraph).
6. **Product (pre-existing gap, found by run 7): the post-deletion cleanup had no retry layer.** The
   indexing probe caught the API's own `vector_index.delete_failed` (`VectorIndexError`) leaving one
   point behind under load. Research: Qdrant's `wait=true` means a *successful* delete is applied, so
   this was a real provider failure; the adapter's own contract says a transient index failure (a
   refused connection, a timeout, a 5xx, a documented 429 delay) is the caller's to retry; the queued
   stages get that retry from the queue, and this path runs outside it. Fixed with
   `application/cleanup.py`, a bounded (3 attempts, growing backoff) retry shared by the vector-index
   and graph cleanups — the two that are correctness problems rather than wasted space, and the two
   whose adapters classify transient failures explicitly. The object cleanup keeps its warning-level
   contract because the storage adapter has no such classification, and retrying an unclassified
   failure is what the plan forbids.

Two further failures were environmental, not code, and are recorded here as such:

* run 6 — the agent probe's own provider re-measurement (`step 10`) hit `httpx.ReadTimeout` on a
  SiliconFlow call. Every *product* assertion before it passed (the SSE contract, citations, the
  bounded rounds, cancellation, the checkpointer tables).
* the same probe passed in runs 3, 5, 8 and 9; the indexing probe passed in runs 3–6, 8 and 9.

## Residual risks and follow-ups (owner decisions, outside this refactor)

1. **"Graph ready" means accepted, not processed.** LightRAG's own status machine is
   `PENDING → PARSING → ANALYZING → PROCESSING → PROCESSED | FAILED`, and its recovery entries are
   `reprocess_failed` / a new insert (documented in `docs/research/official-docs-lightrag.md` §40).
   If graph readiness must mean "processed", the build has to wait on document status; that is a
   behaviour change this refactor does not make.
2. **Cleanup is attempted inline, not scheduled.** The plan's wording is "deletes its business rows
   and *schedules* external cleanup"; the implementation performs it after the commit and reports a
   failure (now with a bounded retry). A durable cleanup job would close the remaining difference —
   a scheduled stage that retries until it succeeds and records its own outcome.
3. **The acceptance suite is load-sensitive.** The two environmental failures above happened in runs
   where the machine had been running probes for ~15 minutes. The suite is green when run on a quiet
   machine, which is what the accepted run shows.
